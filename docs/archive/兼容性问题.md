# DSH + Univer Office 浏览器兼容性适配方案

> 归档：2026-11-06 的原始调研，保留当时的问题假设和建议，未按最终实现逐条改写。本文不作为当前配置或验收结论；请先阅读 [当前兼容性指南](../compatibility.md)。后续核对与修正见 [实施前评估](兼容性评估与实施建议.md)。

**目标环境：Chromium 108 / Chrome 108 / Safari 537.36 UA 标识**

**文档版本：** V1.0<br>
**日期：** 2026-11-06<br>
**文档性质：** 技术方案与实施建议

## 1. 背景与目标

### 1.1 背景

计划在远程 Linux Code Server 环境中部署原版 DeepSeek Harness（DSH），并通过 `dsh-univer-office` 提供 Office 文档的创建、编辑、预览、审阅和导出能力。

实际使用终端包括 Windows 7 工作站，浏览器运行环境受到限制，目标浏览器为 Chromium 108。

服务器端采用现代 Linux 运行环境，不需要为了兼容 Windows 7 而降低 Node.js、DSH 或 Univer SDK 的版本。

主要兼容性问题集中在浏览器客户端：

1. 现代 JavaScript API 在旧版 Chromium 中缺失。
2. DSH 原版前端存在新式 JavaScript API 调用。
3. Univer Viewer 使用 ESNext 构建目标。
4. DSH 和 Univer 样式使用部分较新的 CSS 特性。
5. 浏览器 Worker 拥有独立运行环境，主页面 Polyfill 不会自动生效。
6. 现代 Viewer 的复杂 DOM、Canvas、字体和布局行为需要验证。

### 1.2 适配目标

本方案的目标是：

- 不修改 DSH Agent Loop 和核心业务逻辑。
- 尽量保持 DSH 原版 React/TSX/CSS 及前端 Bundle 不变。
- 在 Host 层建立统一的浏览器兼容基础设施。
- 对 DSH Web UI、Univer Viewer 和 Worker 分别实施兼容适配。
- 以能力检测而不是 User-Agent 判断作为主要兼容策略。
- 通过固定浏览器版本的自动化测试和真实 Win7 浏览器验收。
- 不依赖外部 CDN、在线 Polyfill 服务或互联网资源。

### 1.3 总体原则

采用：

**固定上游前端 + Host 早期注入 + 按需 Polyfill + Viewer 独立构建适配 + Worker Realm 适配 + 浏览器能力验收。**

不建议将旧浏览器兼容问题直接修改到 DSH 或 Univer 的业务源码中，也不建议对整个前端进行大规模降级重写。

## 2. 目标浏览器与兼容性基线

### 2.1 关于 Safari 537.36

需要特别澄清：

典型 Chrome User-Agent：

```text
Mozilla/5.0 (Windows NT 6.1; Win64; x64)
AppleWebKit/537.36 (KHTML, like Gecko)
Chrome/108.0.5359.95 Safari/537.36
```

其中：

- `AppleWebKit/537.36` 是历史兼容标识。
- `Safari/537.36` 是兼容性标识。
- `Chrome/108.0.5359.95` 才是实际浏览器版本信息。

这不意味着浏览器使用 Safari 537 引擎。

因此本方案将 Chromium 108 作为主要兼容基线。

如果实际还需要支持使用 WebKit 537.36 内核的独立浏览器，应单独采集其完整 User-Agent、实际引擎版本和功能探针。不能直接套用 Chromium 108 的兼容结论。

### 2.2 兼容性分层

| 层级 | 运行环境 | 适配策略 |
|---|---|---|
| Server Runtime | Linux + Node.js 22+ | 保持现代运行环境 |
| DSH Host | Node.js DSH | 增加浏览器兼容 Host Bundle |
| DSH Client | Chromium 108 | ES 语法降级、API Polyfill |
| Univer Client | Chromium 108 | ES 语法降级、API Polyfill |
| Univer Viewer | Chromium 108 | 独立构建目标与早期注入 |
| Browser Worker | Chromium 108 Worker Realm | 独立能力适配 |
| Render Machine | Linux Chromium | 保持服务器端现代浏览器环境 |

需要注意：服务器端 Render Machine 和用户浏览器是两个不同的运行环境，不应因为 Win7 浏览器兼容而降低服务器端渲染环境的能力。

## 3. JavaScript API 兼容性分析

### 3.1 已知关键 API

根据 MDN Browser Compatibility Data 及现有 Win7 项目的实际探针，以下能力需要重点关注。

| API | Chrome 最低支持版本 | Chrome 108 | 适配策略 |
|---|---:|---|---|
| AbortSignal.any() | 116 | 不支持 | 必须 Polyfill |
| Promise.withResolvers() | 119 | 不支持 | 必须 Polyfill |
| Array.prototype.toSorted() | 110 | 不支持 | 检查实际调用后补齐 |
| Iterator 构造器 | 122 | 不支持 | 检查实际调用后补齐 |
| CSS color-mix() | 111 | 不支持 | 必须 CSS 适配 |
| AbortSignal.timeout() | 103 | 支持 | 能力检测，不重复覆盖 |
| structuredClone() | 98 | 支持 | 保留原生实现 |
| CSS :has() | 105 | 支持 | 保留原生实现 |
| CSS Container Queries | 105 | 支持 | 保留原生实现 |

版本依据：

- [AbortSignal.any - MDN](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/any_static)
- [Promise.withResolvers - MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/withResolvers)
- [Array.toSorted - MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Array/toSorted)
- [CSS color-mix - MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/color-mix)

注意：表格描述的是浏览器原生支持情况，不代表所有这些 API 都已经在 DSH 和 Univer 的实际生产 Bundle 中被调用。最终 Polyfill 清单必须以实际构建产物和运行调用面为依据。

### 3.2 DSH 核心 API 兼容

优先处理两个已经在 Win7 项目中确认的问题。

**A. AbortSignal.any()**

该 API 用于组合多个取消信号。

DSH 中涉及：

- RemoteStream 生命周期。
- Connection 连接代管理。
- 事件流取消。
- 请求和会话终止。

缺失时可能导致：

```text
RemoteStream.read()
        |
        v
AbortSignal.any()
        |
        v
TypeError
        |
        v
Connection 初始化失败
        |
        v
持续重连
        |
        v
Session 状态同步异常
```

建议直接复用现有项目中经过设计的 `AbortSignal.any()` 兼容实现。

实现要求：

- 支持 Iterable 输入。
- 支持多个 AbortSignal。
- 正确处理已经 aborted 的源信号。
- 保留 abort reason。
- 正确传播第一个有效 abort。
- 清理不再需要的事件监听器。
- 不改变原生实现的行为。
- 不破坏取消和超时语义。

不能仅用简单的 `addEventListener` 组合代替完整的语义实现。

**B. Promise.withResolvers()**

主要用于创建可以从外部控制 resolve/reject 的 Promise。

DSH 中涉及：

- 审批交互。
- 用户提问。
- 异步状态等待。
- Session 控制流程。

建议复用现有 Win7 项目的实现，并验证：

- Promise 创建和状态。
- resolve/reject 的幂等行为。
- Promise 子类构造器。
- 多次调用。
- 动态插件卸载。
- Pending 操作取消。

### 3.3 其他 JavaScript API

Win7 项目的现有兼容层还包含以下潜在适配能力：

- Promise.try
- Math.sumPrecise
- Uint8Array.fromBase64
- Uint8Array.prototype.toBase64
- Uint8Array.prototype.toHex
- Map.prototype.getOrInsert
- Map.prototype.getOrInsertComputed
- Set.prototype.intersection
- ArrayBuffer.prototype.transferToFixedLength
- Iterator

这些 API 部分可能来自 PDF.js 等第三方运行时。

建议先审计 DSH、Univer Viewer 和实际依赖 Bundle，再决定是否纳入兼容层。

不要将所有现代 API 一次性全局 Polyfill。

### 3.4 URL 与自定义协议

之前 Win7 项目还发现过旧版 Chromium 在自定义 URL Scheme 上的行为差异。

尤其需要检查：

```text
dsh-resource://file/...
```

建议：

1. 对 URL 构造器执行能力探针。
2. 测试 hostname、pathname、origin 和序列化行为。
3. 对实际存在问题的实现使用已经审查过的 core-js URL 兼容产物。
4. 保留现代浏览器原生 URL 实现。
5. 检查 DSH 文件引用、附件和 Univer 资源地址。

不能只因为浏览器缺少某个 API 就替换整个 URL 构造器。

## 4. CSS 兼容性策略

### 4.1 color-mix 是重点

Chrome 108 不支持：

```css
color-mix(in srgb, red, blue)
```

而 DSH 原版前端及 Univer Viewer 均有相关样式。

因此这项能力必须处理。

建议优先复用：

```text
deepseek-harness-win7/
└── dsh/
    └── host/
        └── browser_compat/
            └── compat.js
```

其中现有 color-mix fallback 已经实现：

- CSS 变量解析。
- sRGB 混色。
- 透明度处理。
- 动态 Style 插入。
- 主题切换。
- MutationObserver。
- 样式禁用与恢复。
- 监听器和生成样式清理。

但不建议未经性能评估就直接将原实现完整应用到 Univer Viewer。

Univer 表格可能存在大量 DOM 节点，原兼容实现中的全页面元素扫描可能产生额外成本。

建议采用两级策略：

**优先级 A：构建时 CSS 转换**

对于颜色和变量可以静态确定的表达式，在构建时生成兼容声明。

**优先级 B：运行时 CSS fallback**

对于依赖动态主题变量的表达式，使用运行时 fallback。

要求：

- 只处理确实包含 color-mix 的样式。
- 避免无关 DOM 变更触发全页面计算。
- 合并同一帧的样式刷新。
- 支持主题切换。
- 保证卸载时恢复原样式。
- 通过大型 Sheet 的性能测试。

### 4.2 其他 CSS 特性

建议重点审计：

| CSS 特性 | 适配建议 |
|---|---|
| color-mix | 必须处理 |
| scrollbar-width | 提供 WebKit 滚动条样式 fallback |
| light-dark | 检查实际 CSS 调用，必要时替换 |
| scrollend | 使用事件特性检测和 debounce fallback |
| :has | Chrome 108 可原生支持 |
| Container Queries | Chrome 108 可原生支持 |
| CSS Grid / Flexbox | 保留原生实现，检查具体布局差异 |

不建议整体重写 Tailwind CSS 4 生成的样式。

## 6. DSH 主页面适配

### 6.1 Host 早期注入

直接借鉴 Win7 项目的设计。

原版 DSH 提供：

```text
webserver/index-inject
```

兼容 Bundle 通过 Host 插件监听该事件，在 HTML 返回之前注入兼容脚本。

建议采用本地静态 JS 文件：

```text
/assets/dsh-browser-compat.js
```

而不是从 CDN 下载。

注入要求：

1. 在所有客户端模块之前执行。
2. 不使用 async 或 defer。
3. 保证兼容脚本只注入一次。
4. 确保 CSP 允许加载本地脚本。
5. 在最终 HTML 上检查注入顺序。
6. 对脚本版本和 SHA-256 做记录。

现代浏览器中通过能力检测跳过 Polyfill，不覆盖原生 API。

### 6.2 不修改 DSH 核心

不建议直接修改：

- RemoteStream
- Connection
- Session
- Agent Loop
- 模型选择器
- 审批组件
- 用户提问组件

这些属于上游业务逻辑。

应通过 Host 提供的 HTML 注入机制补齐浏览器运行能力。

这样未来升级 DSH 时，只需要维护兼容 Bundle，而不需要重复合并业务代码补丁。

## 7. Univer Viewer 独立适配

### 7.1 为什么需要独立处理

`dsh-univer-office` 的 Viewer 并不是 DSH 主页面的一部分。

目前的结构是：

```text
Win7 Browser
    |
    v
DSH Web Server
    |
    +-- DSH index.html
    |
    +-- /univer-viewer/*
              |
              v
        Viewer Proxy
              |
              v
        Local Gateway
              |
              v
        Viewer Static Assets
```

Viewer Proxy 当前采用 HTTP 流式转发，不会自动继承 DSH 主页面的 HTML 注入。

因此，仅在 DSH Host 注入 Polyfill 不足以覆盖 Univer Viewer。

### 7.2 Viewer 构建目标调整

目前 `dsh-univer-office/scripts/build.mjs` 中：

| 构建目标 | 当前配置 |
|---|---|
| DSH Client | ES2022 |
| Viewer | ESNext |
| Render Machine | ESNext |

建议将 Viewer 改为：

```js
build: {
  target: 'chrome108',
  outDir: viewerOut,
  emptyOutDir: true
}
```

同时对 DSH Client 的最终构建产物进行 Chrome 108 目标审计，必要时将构建目标明确设置为：

```js
target: 'chrome108'
```

Render Machine 运行在服务器端浏览器环境中，不需要因为 Win7 浏览器而降级。

### 7.3 Viewer 早期注入

建议通过 Vite HTML 构建插件，在 Viewer 的 index.html 中注入：

```html
<script src="/univer-viewer/compat/browser-compat.js"></script>
```

要求：

- 作为普通同步脚本执行。
- 先于 Viewer 的 Module Script。
- 不依赖远程 CDN。
- 确保相对资源路径正确。
- 支持 Viewer CSP。
- 与 DSH Host 使用同一份兼容能力定义。

建议将 Viewer 构建产物、兼容脚本和版本号作为一个完整交付单元。

### 7.4 第三方 SDK 兼容

需要重点检查：

- Univer Core。
- Univer Docs。
- Univer Sheets。
- Univer Slides。
- Univer Collaboration。
- Comparison Viewer。
- Tailwind CSS 4 产物。
- 第三方 PDF、图标及编辑组件。

不能只审计 Viewer 的入口文件。

必须覆盖最终浏览器加载的全部 JS、CSS、动态 Chunk 和实际启用的 Worker。

## 8. Worker 兼容性

### 8.1 独立 Realm 问题

浏览器 Worker 拥有独立的 JavaScript 全局环境。

主页面注入的：

```javascript
Promise.withResolvers
AbortSignal.any
```

不会自动进入 Worker。

因此需要针对实际使用的 Worker 建立兼容机制。

### 8.2 借鉴现有实现

Win7 项目已有：

```text
dsh/host/browser_compat/worker.js
```

该实现通过识别指定 Blob Worker、包装 Worker 创建过程、前置兼容脚本和管理 Blob URL 生命周期实现 Worker 适配。

但它目前针对 DSH 自己的特定 Worker，不能直接假定 Univer 使用相同的 Worker 类型。

### 8.3 本次建议

先通过浏览器调试记录：

- Worker 构造函数。
- Worker URL。
- Worker 类型。
- Blob URL。
- Worker 名称。
- Worker 创建与销毁。
- Worker 内部首个异常。

根据实际结果决定：

1. Worker 构建时内嵌 Polyfill。
2. Blob Worker 创建时注入 Bootstrap。
3. Module Worker 入口增加兼容模块。
4. 不需要兼容的 Worker 保持原样。

不要未经审计全局替换 Worker 构造器。

## 9. Code Server 自身的兼容性

Code Server 本身也是独立的 Web 应用。

即使 DSH 和 Univer 已经完成 Chrome 108 适配，也不能直接推断 Code Server 的编辑器、Monaco、文件树和扩展 WebView 一定兼容。

因此需要将 Code Server 单独列为浏览器验收对象。

重点测试：

- Code Server 登录。
- Workspace 文件树。
- Monaco 编辑器。
- 终端。
- 文件上传下载。
- WebSocket。
- 页面刷新恢复。
- 插件 WebView。

建议固定 Code Server 版本，不要在没有测试的情况下自动升级。

## 10. 浏览器网络与运行环境

由于 Win7 只承担浏览器客户端，Linux 负责所有服务端计算，网络和安全配置也需要单独验证。

### 10.1 网络

- 使用内网 HTTPS。
- 证书链能够被 Win7 信任。
- WebSocket Upgrade 正常。
- Session 长连接稳定。
- 支持页面刷新后的重新鉴权。
- DSH 和 Viewer 尽可能保持同源。
- 不依赖外部 CDN。

### 10.2 字体

需要区分两套字体环境：

**Win7 客户端：**

负责 Viewer 页面、Canvas 和编辑界面的字体显示。需要确认本机中文字体安装情况。

**Linux 服务端：**

负责 Chromium Screenshot、PDF 和布局检查。需要安装中文字体、fontconfig 等。

两者字体不一致可能造成：

- 文本换行变化。
- PPT 文本溢出。
- 文档分页差异。
- Canvas 文字测量差异。

因此，字体应作为明确的部署依赖进行管理。

## 13. 风险与边界

| 风险 | 应对策略 |
|---|---|
| 第三方 SDK 使用新 API | 对最终 Bundle 做静态审计和动态运行检查 |
| Viewer 使用 ESNext | 修改构建目标 |
| Worker 缺少 Polyfill | 独立 Realm 适配 |
| color-mix 性能影响 | 优先构建时转换，运行时适配需性能测试 |
| 字体差异 | 分别管理客户端和服务端字体 |
| Code Server 不兼容 | 单独固定版本和验收 |
| CSP 阻止兼容脚本 | 使用本地静态脚本并检查 CSP |
| 外网资源依赖 | 离线打包和缓存 |
| 现代浏览器回归 | 通过能力检测保留原生实现 |

本方案不承诺所有现代 Web 特性均能通过 Polyfill 补齐。对于无法合理降级的语法、渲染能力或第三方组件，需要单独评估替代实现或功能降级。

特别是如果实际目标是独立的旧版 WebKit 537.36，而不是 Chrome UA 中的 Safari/537.36 标识，则应重新确定浏览器基线。该环境不能直接套用 Chrome 108 方案。

## 14. 最终建议

建议采用：

**一个独立的 DSH Browser Compatibility Bundle + 一个 Univer Viewer Chrome 108 兼容构建。**

具体职责：

- DSH Host Bundle：负责主页面早期注入、能力探针和通用 JS Polyfill。
- Univer Viewer Build：负责 Viewer 自身语法目标、独立页面注入和 CSS 适配。
- Worker Adapter：负责独立 Realm 的必要兼容。
- Browser Audit：负责能力差异、构建产物和运行行为的持续检查。

复用 `deepseek-harness-win7` 的既有成果，但不迁移其 Python Host 或 Windows 专用运行逻辑。

最终形成：

```text
Remote Linux
    |
    +-- Code Server
    |
    +-- Original DSH
    |      |
    |      +-- Browser Compatibility Bundle
    |      |
    |      +-- dsh-univer-office
    |                 |
    |                 +-- Chrome 108 Viewer Build
    |                 +-- Viewer Compatibility Adapter
    |                 +-- Gateway
    |                 +-- Workers
    |
    +-- Internal LLM API

Windows 7
    |
    +-- Chrome 108
           |
           +-- Code Server UI
           +-- DSH Web UI
           +-- Univer Viewer
```

核心原则是：**服务端保持现代化，浏览器端按能力适配，业务代码保持上游原貌，兼容能力集中管理。**
