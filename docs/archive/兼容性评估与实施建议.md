# Chromium 108 兼容性评估与实施建议

> 归档：本文描述实施前配置和基线，文中的“当前”均指评估时状态，备选方案不等于最终部署方案。最终采用 code-server 子域名 forwarding 和最小 API 注入，当前结果见 [兼容性指南](../compatibility.md)。静态发现的 CSS 或 API 风险不代表已经复现故障。

评估日期：2026-11-06。依据：`兼容性问题.md`、当前仓库配置、已构建镜像中的实际前端产物，以及文末上游资料。

实施状态：已完成 forwarding 和最小 API 注入，并使用新镜像通过 Chromium 108 与现代浏览器的基础表格流程。下文保留实施前的评估基线，最新版本、实测结果和验收边界见 [兼容性指南](../compatibility.md)。

## 1. 结论

原调研的方向基本正确：服务端保持现代运行环境，客户端分别适配 DSH 主页面、Office Viewer、浏览器 Worker，并以真实 Chromium 108 验收。按用户确认的策略，尽可能使用上游最新版，优先用少量、基于能力检测的前端预先注入解决问题；只有实际测试证明必要时，才增加局部构建或样式处理。

当前项目需要额外处理三个具体问题：

1. **Office 的根路径与现有 `/dsh/` 反代不匹配；改用 code-server 默认子路径 forwarding 也不能自动解决，但子域名 forwarding 可以避免该类路径问题。**
2. **CSS 适配必须覆盖实际出现的 `oklch()`、`light-dark()` 和不同颜色空间的 `color-mix()`，不能只处理 sRGB 混色。**
3. **Kilo Code 的网页视图也存在 Chromium 108 缺失 API 的直接调用，不能只验收 code-server 外壳。**

建议实施顺序：确认 forwarding 入口 → DSH 和 Office 最小预先注入 → Chromium 108 关键流程验证 → 按实际故障补充 CSS、语法或 Worker 适配。code-server/Kilo/OpenCode 的问题单独记录，不作为 DSH 兼容层实施前必须改动其他组件的理由。

## 3. 按优先级处理

### P0：区分当前入口与 code-server forwarding

在 code-server 终端启动进程，与浏览器通过哪个代理访问，是两件事。当前 `scripts/dsh-web.sh` 明确设置 `--public-url .../dsh/`，文档也要求打开该地址，因此仓库目前实际配置的是 Nginx 直接转发 DSH，不是 code-server forwarding。

code-server 确实自带 forwarding，无须给每个应用单独增加 Nginx 路由。但两种 forwarding 模式行为不同：

| 入口 | Office 根路径的行为 | 本次验证 |
| --- | --- | --- |
| 当前 `/dsh/` 独立 Nginx 规则 | `/univer-viewer/...` 跳出 `/dsh/`，落到 code-server | 配置及 Office 产物核对 |
| 默认 `/proxy/3080/` | 同样跳出 `/proxy/3080/`；代理不重写 HTML、JS 中的绝对 URL | `/proxy/3080/` 返回 200，根路径探针返回 404，手动加回 `/proxy/3080/` 后返回 200 |
| code-server 子域名 forwarding | 整个子域名根路径转发至同一端口，保留 Office 现有根路径 | 根页面、`/univer-viewer/...`、`/univer-api/...`、`/uf/...` 探针均到达上游并返回 200 |

测试直接访问镜像内 code-server，未经过部署中的 Nginx，因而默认子路径的失败不是 Nginx 独立规则造成的。已检查的 code-server `pathProxy.js` 与 `proxy.js` 也与结果一致：剥离代理前缀并转发请求，对部分 Location 重定向补前缀，不对响应正文中的资源 URL 做重写。`/absproxy/3080/` 也不是通用的正文 URL 修复器。

**按用户希望通过 code-server forwarding 的架构，优先采用子域名 forwarding。**现有 Nginx 继续统一转给 code-server，由 code-server 按 Host 分流端口，不需要为 Office 的各个 API 增加独立 Nginx 规则。需要配置 code-server 的 `proxy-domain`、对应 DNS/hosts 与证书，并将 DSH 的公开 URL 和 trusted host 指向该 forwarding 域名。当前外部使用 8443，实施时必须核对 Host 中的端口与匹配模板；本次子域名探针的模板包含测试端口。

另有一个实际连接前提：当前 `dsh-web` 监听容器接口 IP，是为 Nginx 跨容器连接准备的；当前版本 code-server 内置代理的目标是 `0.0.0.0:<port>`。实测仅监听接口 IP 的服务不能通过此目标连接，而监听 `127.0.0.1` 的探针可正常代理。因此改用内置 forwarding 时应让 DSH 监听 `127.0.0.1`，同步调整启动脚本，不能只换浏览器地址。

若部署只有单个 IP/主机名，且不能增加 forwarding 子域名，则默认子路径仍需要 Office 完整支持公共前缀，或采用下面的显式路由修复；不能认定默认端口转发会自动适配绝对 URL。

以下是当前独立 `/dsh/` 配置的具体证据与备选修复，并非要求继续使用独立 Nginx 路由：

已确认以下配置和产物事实：

- `configs/nginx.conf` 只将 `/dsh/` 转发到 DSH，并剥离该前缀；其他普通根路径进入 code-server。
- 同一处配置将上游 Cookie 的 `Path=/` 改写成 `/dsh/`。
- Office Viewer 的 HTML 直接引用 `/univer-viewer/assets/...`。
- Office 的服务端常量及随包部署说明使用 `/univer-viewer`、`/univer-api`、`/uf`；协作 WebSocket 使用 `/univer-viewer/ws`。
- DSH 当前认证实现设置的 Cookie 原始路径为 `/`。Office 上述入口复用 DSH 的浏览器鉴权。

因此当前配置会把 Office 的根路径请求送往错误服务；即使补上转发，只保留 `/dsh/` Cookie Path，浏览器访问这些根路径也不会携带该 Cookie。这是部署配置问题，与 Chromium 108 无关。

**保留当前独立 Nginx 布局时的备选修复：**为 Office 的上述根路径及其边界增加指向 DSH 的转发，保留原始路径，正确转发 WebSocket 和查询参数；取消将 DSH 认证 Cookie 缩窄到 `/dsh/` 的改写。随后验证首次登录、Viewer 首次打开、刷新、HTTP API 和 WSS 鉴权。继续由 DSH 执行 Host、Origin、Cookie 及会话范围检查。改走 code-server forwarding 后不会经过这条 `/dsh/` Cookie 改写规则，不能把该规则的问题照搬到 forwarding 方案上。

**长期更清晰的布局：**给 DSH 单独的主机名，在其根路径部署 DSH 和 Office；可与现有服务共用 8443 端口，由 Nginx 按主机名分流。这需要同步配置 DNS、证书、公开 URL 和可信 Host。

如果要求所有 Office URL 也严格落在 `/dsh/` 下，就需要上游端到端支持公共前缀，包括 Viewer 构建 base、API、状态投影、WebSocket 和 Cookie。仅修改 `proxy_pass` 或给 HTML 做字符串替换不完整。

### 版本策略：最新版优先，记录实际安装结果

用户希望尽可能使用最新版。少量基于 Web 标准 API 和能力检测的预先注入，不要求固定基础镜像、CLI 或全部扩展版本。此前把全面锁定版本列为 P0 前提过于保守，现撤回这一要求。

继续使用最新上游组件；构建时记录实际安装版本和镜像 ID，升级后运行少量兼容冒烟检查即可。只有需要按特定源码结构打补丁或重建前端时，才记录该次补丁对应的源码提交及锁文件，不因此冻结其他组件。测试持久化扩展卷时应确认实际加载版本，因为已有卷不一定自动采用新镜像内的插件或扩展版本。本次没有改动安装版本配置。

### P1：DSH 的早期兼容脚本可行，但应按真实依赖补齐

当前已安装的 `dsh-host-webserver` 确实提供 `webserver/index-inject`。实现会把 head 注入内容插在 `<head>` 开始位置，适合在应用模块执行前加载本地同步脚本，原调研的 Host 插件方案有实际接口支撑。

当前 DSH 客户端相关产物包含 `AbortSignal.any`、`Promise.withResolvers`、`toSorted`，并在部分预览/插件市场产物中出现 `URL.parse`、`URL.canParse`。前三项应作为第一批验证和补齐对象；URL 方法需检查具体调用及已有保护后决定。

实施要求：

- 使用能力检测，仅在缺失时安装；脚本自身按 Chromium 108 可解析语法构建。
- 选用有标准语义测试的实现，覆盖取消原因、已取消信号、空输入、监听器清理及数组排序语义。
- 不整体替换原生 `URL`，不因为扫描到名称就一次性加入所有新提案 API。
- 确认真实响应中的执行顺序、静态资源路径和 CSP；本地脚本也不自动获得 CSP 放行。
- 兼容能力按页面生命周期安装一次；插件卸载时清理监听和观察器，不在其他组件仍运行时删除已经使用的全局 API。

原文引用的 Win7 兼容实现可作为候选，但本次未能取得其源码完成审查，不应直接认定可以原样迁移。

### P1：Office 需要独立构建和完整 CSS 适配

先给独立 Viewer 同步预先注入，再用 Chromium 108 验证是否存在语法解析错误。`esnext` 是风险线索，不等于当前 bundle 一定无法解析。只有实测出现无法由运行时补丁解决的语法问题，才基于当时最新版源码调整浏览器端目标至 `chrome108`，保留独立的服务端及渲染机目标。上游当前构建脚本分别配置了 DSH 客户端、Viewer、Gateway、Node Worker 和 render-machine，不能对所有 target 一刀切。

`target: chrome108` 主要解决 JavaScript 语法，**不会自动补齐运行时 API，也不能据此认定 CSS 已兼容**。当前 npm 安装产物不包含完整源码构建工程；不能假设在容器里修改一个构建参数后即可重建。

实际 Viewer 产物中存在 `toSorted`，以及 `color-mix()`、`oklch()` 等样式。DSH 客户端和 Kilo 还出现 `light-dark()`；Kilo diff 样式使用 `color-mix(in lab, ...)`。仅支持 `in srgb` 的补丁无法覆盖这些场景。

CSS 建议采用以下方式：

1. 静态颜色在构建时输出 Chromium 108 可用的颜色值；对动态主题提供明确的浅色/深色变量与声明。
2. 对不能静态求值的表达式，再使用限定到相关样式和主题变量的运行时适配；覆盖 JS 注入的 CSS 及动态加载样式。
3. 逐项检查转换后的视觉语义，尤其是文字、透明背景、选区、diff、菜单、弹层和中文字体。
4. 不对整棵 DOM 的每次变化全量扫描或计算样式，避免大表格中的额外开销。

Tailwind v4 官方浏览器基线为 Chrome 111，其产物不能默认视为支持 108。另一方面，不能把所有新式 CSS 都列为故障：`@property`、`@layer` 本身已在 108 之前支持；应检查其具体声明，而非见到规则就删除。原文的 Container Queries 支持结论也应限定到具体查询类型。

### P1：Kilo 与 code-server 分别验收

Kilo 7.8.27 的 `dist/webview.js` 和 `dist/diff-viewer.js` 存在 `Promise.withResolvers()` 调用；已检查到网页视图请求逻辑中的直接调用。这是需要实际验证的明确依赖，不能用“扩展安装成功”替代兼容结论。

DSH 的兼容注入不会自动进入 Kilo 网页视图。Office Viewer iframe、code-server、Kilo 网页视图和浏览器 Worker 都有各自的执行环境及资源加载策略。

处理顺序应是：先测当前最新版，确认实际失败入口；必要时在 Kilo 自身启动入口注入兼容实现，同时处理实际影响使用的样式。Kilo 作为独立观察项，不扩大成 DSH 兼容层必须改动的范围，也不据此要求降级 code-server 或固定其他组件版本。

验收 code-server 时应覆盖编辑、终端输入输出、文件树、中文输入、扩展启动及刷新重连；验收 Kilo 时覆盖配置、模型请求、流式消息、工具确认和 diff。OpenCode GUI 也要单独打开验证。

### P2：Worker、字体与实际 Win7 环境按需处理

原调研关于独立 Worker 环境的判断正确。但 Office 同时包含 Node Worker，不能把名称含 Worker 的产物全部按浏览器处理。

先记录实际浏览器 Worker 的 URL、类型、异常和 API，再修改对应入口。经典 Worker 和模块 Worker 使用各自合适的加载方式；不统一劫持全局 `Worker` 构造器。

服务端安装中文字体只解决服务端渲染的一部分问题。客户端 Office 的 Canvas、文字度量和导出预览仍应在 Win7 上检查；需要一致字体时，明确客户端字体资源，并等待字体加载完成再比较排版。

## 4. 建议拆成四个可验收的改动

| 改动 | 主要内容 | 完成标准 |
| --- | --- | --- |
| 一：forwarding 与基线 | code-server 子域名 forwarding、DSH 监听地址与公开 URL；记录实际版本和浏览器内核 | 现代浏览器登录后完成 Office 打开、编辑、保存和刷新；资源与鉴权路径正确 |
| 二：DSH 兼容插件 | 本地早期注入、必要 API、主页面样式 | Chromium 108 完成会话、流式输出、审批、取消、刷新重连 |
| 三：Office 最小适配 | 独立注入、必要 CSS；仅在实测需要时调整语法目标或浏览器 Worker | 108 完成所需文档类型的编辑、审阅、导入导出和协作连接 |
| 四：目标环境回归 | 真实 Win7、现代浏览器；IDE 和其他扩展问题单独记录 | DSH/Office 关键工作流通过，升级后冒烟检查可重复执行 |

不建议一开始就制作庞大的通用 CSS/Worker 自动修复框架，也不要求冻结项目依赖。先在最新上游组件上通过少量预先注入跑通关键流程，再根据实际故障决定是否补充适配。

## 5. 验收与当前未决项

必须使用真实的 Chromium 108 内核做自动化，而不是用最新 Chromium 修改 User-Agent。Linux 108 可用于回归，但不能替代 Win7 实际浏览器的字体、GPU、输入法和证书验证。

验收至少记录：浏览器产品和内核完整版本、操作系统、镜像 ID、扩展实际版本、控制台异常、失败请求、WebSocket 连接，以及关键操作结果。记录适配前后同一组场景，避免将已有服务端或路由故障误判为浏览器问题。

当前尚不能确认：目标 Win7 浏览器的完整版本和定制补丁、哪些缺失 API 已有可达的上游 fallback、108 下的具体语法异常、Office 大文档性能，以及 Kilo 网页视图和输入法的实际表现。因此本报告给出的是有产物依据的修复方案，不是兼容性验收通过证明。
